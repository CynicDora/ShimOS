# ShimOS 第三轮完整架构评估

> 2026-10-20 完成版。已复核旧 round1，实际完成本轮26个正式VM块、350个产品会话及对应资格、失败分析和留出验证。失败、未知指标与尚未覆盖的安全范围均保留，不将它们视为成功结果。

本轮发现的主要规律是：**需要很多新域、每域任务少时，共享跨域模板有价值；一个可信域可以处理很多请求时，域内模板开始更划算；允许保留业务进程且能够正确重置已知状态时，持久 Worker 又能省去一部分派生成本。** 三种选择对应不同隔离和状态合同，不能合成一个脱离前提的排行榜。

## 2. 真实架构与公平性边界

| 架构 | 域与进程组织 | 状态边界及代价 |
|---|---|---|
| G0 原生冷启动 | 每请求新 Bubblewrap 域和新 Python；授权后初始化 NumPy | 不保留应用状态；具备原 round1 的 H、出生归属、wait、EOF 与最终回收合同 |
| G1 跨域 Cold | 每请求新 Z，经过 Z→S→W；授权后由 W 初始化 | 用于分离跨域执行链和初始化复用的成本 |
| G2 跨域 Warm | 一个可信外部 Z；每请求新 S/W；本轮密度实验可在同一域运行 K 次 | 每请求独立进程；外部模板具有跨域管理资格，只允许固定可信依赖 |
| G3 域内 Zygote | 每域一个预热 Z；在域内用完整 fork runtime 派生新 W | 不需要逐请求 S 跨域切换；每域重复初始化模板；业务写入不反馈到模板 |
| G4 持久 Worker | 同域同一 Python/NumPy 进程接受固定请求 | 每请求函数返回及已知状态 reset；只有最终真实 wait，不伪称逐请求进程退出 |

G2/G3 的 D、K、输入和域保留政策相同。密度实验的 D 个域按顺序创建、使用和销毁，G3 同时只保留一个模板；不能把 D=50 的累计初始化说成同时常驻 50 个模板。多域同时存活由并发实验单独验证。

G4 仅适用于同信任主体、固定函数和可枚举状态恢复范围。已验证数组、模块状态、NumPy 配置、FD、线程、环境、信号等声明检查，并在取消或不可恢复状态时结束实例；没有任意 Python 堆清洗、跨租户共享或任意依赖安全保证。

涉及 Python 内存派生的 G1/G2/G3 使用 glibc D 完整 fork wrapper 与 CPython hooks；G0/T2 是冷 exec 路径，G4 不在每请求派生。各组按声明合同保留 Bubblewrap 目标域、原子 cgroup 出生、授权门禁、namespace/capability/NNP/seccomp、真实 wait、私有回执、输出 EOF、UNKNOWN 和产品自身回收。H 存活及固定 VM 仍是合同前提，不能把实验通过扩大成宿主故障下的生产保证。实现与逐路径责任见[实现合同索引](implementation-and-contract-index.md)。

## 3. 环境与计量口径

固定 KVM 4 vCPU、4 GiB，一次只运行一个实验 VM；C=8 是四核资源竞争，不是八核机器。Kernel 为冻结的 6.18.49-agentic-runtime-opt-v1；Bubblewrap 0.13.1、CPython 3.10.12、glibc candidate D、NumPy 2.2.6 / OpenBLAS 0.3.29 CPU 单线程配置保持固定。来源、实际命令、构建产物、rootfs、动态库及 SHA 位于每个 run 的 manifest 和 frozen 目录。

主 NumPy 时间为同 guest 单调时钟的 **H 创建前→H 被真实 wait**，计入 Z 初始化、建域、业务、输出、wait、回收和会话关闭。共享 fixture 安装、构建和独立冷参考计算在产品会话外，单独记录；因此“冷”指新应用进程及初始化，不是人为清空 Linux page cache。三组不接受不同的免费应用预热。

请求内 call、业务许可、实际计算、资源结束、response-ready 和 response-commit 分开。并发路径保守地在批尾验证模板/FD 后才提交结果；不能用较快的全序列吞吐冒充较快的在线逐请求返回。阶段区间存在包含和重叠，不相加当完整时间，不把 syscall wall 当内核 CPU。

NumPy CPU 主账本使用整个产品根 cgroup 的层级 usage，不再叠加子组；这是该资源域的记账 CPU，不是包含宿主与夹具的全系统 CPU。H/R/Z/S/W 角色明细另列；进程首末采样外的 CPU、故障中断缺样和无法识别的部分保持缺失，不以部分角色之和冒充完整总量。Tool 的 CPU 边界另见第10节。内存同时保留时点 RSS/PSS、Private_Dirty、根记账 current/peak 和观察到的 MiB·s。PSS 采样非原子且覆盖有限，不把 RSS 相加、不以覆盖率外推积分，**全系统净物理内存节省仍为 Unknown**。

21个正式 NumPy VM 的宿主监测完整窗口（包含共同fixture及产品）中，I/O PSI avg10最大值最高49.77%，memory PSI最高9.41%，可用内存最低46.91GiB。宿主并非无I/O压力的理想环境；这些峰值可能包含本实验部署/输出及其他活动，不能反推某个guest阶段的外部噪声因果贡献。未据此删除样本；对毫秒级或接近差异只报告受测值，不宣称稳健优势。见逐VM宿主压力 (`../analysis/formal-host-pressure-01/host-pressure.csv`, omitted from this source release)。

正式性能关闭 ftrace/native callback audit，计时缓冲有界；重型探针独立运行。低干扰不等于零成本：固定数值验证、指纹、参考输出保存、状态和回收检查仍计入。采样开销及缺失事件见各阶段报告，全部慢样本、反向结果和宿主压力记录保留。

## 4. G0/G1/G2：全新独立域中的实际价值

旧 round1 经实际文件复核后保留：N=100 完整序列中位数分别为 G0 **53.793 s**、G1 **61.759 s**、G2 **22.503 s**。同 VM G0−G2 配对节省中位数 31.290 s（26.044–31.483），G1−G2 为 38.112 s（31.076–39.894）。对应根 CPU 中位数 49.679、55.805、16.904 s。

G2 在 N=1 比 G0 慢，N=2 是原受测点中首次三块都正向，但最小差额约167ms；不能把“2次”当通用回本阈值。收益包含避免重复 Python/Z 创建、NumPy 初始化、运行时检查与退出，不能全部归为 import。G1 冷路径较贵说明两次跨域派生链本身也有成本。

G2 N100 根记账峰值约61.27MiB，高于 G0 的45.46MiB；记账内存时间中位数更低，但存在反向块。旧 round1 对齐了每任务预算，没有施加共同的全会话硬内存预算，不能据此推出同总预算的吞吐优势。速度、CPU、峰值、积分和净物理占用不是同一个指标。详见旧结果的本轮综合复核 (`round1-density-persistent-synthesis.md`, omitted from this source release)。

|---|---:|---:|---:|
| 50/1 | 11.644 | 30.608 | −18.969 |
| 25/2 | 10.651 | 18.623 | −8.035 |
| 10/5 | 10.065 | 11.331 | −1.503 |
| 5/10 | 9.791 | 8.979 | +0.789 |
| 2/25 | 9.337 | 7.697 | +1.854 |
| 1/50 | 9.797 | 7.016 | +2.811 |

K≤5 的已测点三个块都由 G2 胜出；K≥10 的已测点三个块都由 G3 胜出。**观测交叉区间是 K5–10，不是精确最优阈值。** G2 避免每域重复模板初始化；G3 在同域高密度请求下可摊销初始化，并使用较短的本地派生路径。这个解释与实现一致，但完整差额不是纯 fork 或 setns 的因果成本。

资源目标也有分歧：K5 时 G2 时间和 CPU 更少，根记账内存时间却更多。模板初始化时点 PSS 两组约39MiB，整会话 PSS 配对因覆盖不足全部不合格；不能借单点或少一个模板便宣称精确的净物理节省。[完整数据与图](../01_cross_vs_local/results-v2.md)。

## 6. G3/G4：省下派生，但状态恢复有合同和成本

K≥5 的 readonly/full 两种任务中，受测配对全部 G4 更快。K100：readonly G3/G4 为14.022/8.604s，full 为14.628/8.663s；配对节省分别5.352/5.447s。readonly K1 保留一次 G4 更慢0.398s的反向样本，单次调用没有稳定收益结论。

G4 reset 约14.5–14.9ms/请求，K100 累计约1.46–1.50s，已计入总时间；它包括已知写入恢复、指纹和验证，不是零开销。1146次实际 reset 均符合固定状态检查。G4 K100 中，同一已预热 Worker 的首请求业务前→末请求业务后时点 PSS 增长约1MiB；末次 reset 后未采样，且K1也出现类似增长，不能据此判线性泄漏或证明无限长期稳定。

G4 根峰值随K从约41MiB增到50MiB；G3也有控制、模板、短命Worker等成本。这是受限持久任务合同下的优势，不是对新进程状态隔离的等价替代。[完整 CPU、reset、污染及内存结果](../02_local_vs_persistent/results-v2.md)。

## 7. 初始化、模板大小、写入和计算量

四个预热层次均实际准入，最终业务相同，缺失初始化在获授权 W 内补齐。N10 时 G2 的 base/import/data/blas 完整中位数为4.646/2.482/3.008/2.752s；预热更多并非单调更快。冷组仍执行完整初始化，不能把 profile 标签误当减少业务工作。

独立初始化诊断将 import、数组构造、BLAS 与指纹分开。G2 blas Z 的8/32/128MiB单次诊断中，NumPy import约235–278ms、BLAS warmup约1.2ms；数组构造约2.6/9.2/49.4ms，SHA约7.3/28.8/115.5ms。它们是小样本诊断，不能替换无重型诊断的正式成绩。

8→32→128MiB 时，G2 N10 完整中位数2.752→4.339→10.476s，G3 6.304→7.751→13.743s；128MiB获得实际资格，未降低限制或改用备选档。变化同时包含数组、哈希、保存和读写，不是单纯页表/fork曲线。

32MiB readonly 到全量写入，G2 完整中位数4.339→4.467s；Worker 观测 Private_Dirty 增量约9.2→41.3MiB，minor faults约2444→10635。只写一个元素、稀疏跨页、每页及全量分别保留实际字节/页面范围；pagemap/exclusive不被解释成精确物理COW拷贝数。readonly也有计算、输出和诊断造成的私有页，不能把所有增量归给继承数组。

light→heavy 时 G2 N10完整中位数2.752→4.443s，纯数值 span约1.97→97.92ms/请求；节省占完整成本的比例随业务变重而缩小；light/heavy 的 G0−G2 配对绝对节省约2.815/2.737s，不构成所有强度下的单调关系。完整对照仍显示收益，但不能推出任意重任务都有同样百分比。[全部1020次结果、局部归因及图](../03_initialization_cow/results-v2.md)。

## 9. 混合模板：静态策略的切换成本

一个模板槽，固定两个已准入profile（import与blas），按精确key静态选择。集中/交替/高低频三模式实际 hit/miss分别14/2、0/16、12/4；N16完整中位数4.645/11.198/5.565s。交替相对集中的同VM额外成本为6.564/6.650/6.312s，模板退出、重新初始化和最终关闭完整计费。

这说明有限槽位及切换规则能产生显著成本，不证明依赖感知算法已有效。精确key不命中是本次策略定义，不代表两个profile不兼容；blas状态能否合法用于另一类请求需要单独准入。高低频模式任务比例不同，不作为纯排序的因果对照。[实际切换、模板内存和等待](../05_mixed_templates/results-v3.md)。

## 10. Tool Exec 独立对照

T1 使用外部 Z→S→W，W 获授权后原位 exec 原 launcher 及工具；T2 使用 Bubblewrap PID1→静态 native gate→同一 launcher/工具，不经过 Python 堆。两组通过同版 14 VM / 108 次故障与安全资格，使用 Tool followup 的较强 H 合同，不与 NumPy 的 H 合同混排。首个 T2 pilot 的正常末端 EOF 竞态 FAIL 保留；修复只在授权完成、DRAINED 与真实回收条件成立时接受终端 EOF，没有把异常通道关闭改成成功。

正式五工具先完成3个同VM配对块。两类 ELF 出现较大反向差值后，预登记仅追加2块、固定停止，不删除旧样本或追测到获胜。最终5VM、38会话、114请求；每会话固定3请求，主时间包含该会话 H/Z 启动及最终关闭。

|静态ELF|5|0.594|0.311|0.285|−0.497～1.062|4/5|
|动态ELF|5|0.602|0.305|0.301|−0.528～0.337|4/5|

这是**3请求完整会话**的差额，不能除以3便称纯启动或fork成本。T2在受测场景减少了控制链与一次会话 Python/Z 准备，但 ELF 的两次反向样本依然存在，没有证明所有工具的完整延迟都稳定改善。五个 Tool VM 的宿主完整监测窗口 IO/memory PSI avg10 最高16.02%/4.67%；窗口包括fixture，不能据此解释某个反向样本的因果来源。

19个实际配对的 H 观测 CPU 差额都为正，各工具中位节省约0.256–0.276 CPU s。该指标是 H 两次 `getrusage` 之间的自身增量，加已经逐级真实 wait 的后代 CPU；不再加 R 或任务 cgroup。H 首次采样前、最后采样后及fixture的CPU未覆盖，不称全系统CPU。完整wall的端点与该CPU观测区间也不完全相同。

保留局部 PSS、角色和任务 cgroup 峰值；没有充分的全会话同步PSS/内存积分，系统净物理内存和完整Tool内存时间保持Unknown。`trace=0`性能样本只核验当次控制回执、真实wait和释放，并绑定精确版本的已运行exec资格，没有伪造新的内核exec观测。exec会替换Python映像，gcc/Shell不能直接继承NumPy堆获得初始化复用。详见[全部配对、初始化/回收分解、CPU及失败](../06_tool_exec_native/results-v1.md)。

## 11. 成本模型与未解释部分

采用有限结构：共享模板路径约为一次模板初始化＋D次建域＋N次跨域执行及管理；域内路径还需D次模板初始化，但每请求本地执行可能较便宜。拟合系数是受测范围的边际趋势，包含串行控制、诊断、验证与回收；不是把重叠span相加、也不是纯内核成本。

已完成的size留出：8/128MiB训练、32MiB验证，G2/G3完整时间MAPE约2.43%/0.45%；记账内存时间误差却约56%/44%，有负截距，原样保留。G0/G1缺少大小变化样本，模型BLOCKED。

前瞻并发模型只用light C1/C2训练，C4/C8留出；G2/G3 MAPE约12.30%/5.00%。固定C4=C8的简化与真实配对不符，不能据此预测最佳并发。未把heavy、压力失败或混合模板填进公式。

N32密度留出已完成：G2/G3 完整时间 MAPE 为4.25%/3.01%；K4时G2、K8时G3在三个实际VM块都更短。模型没有精确定位通用阈值；六个时间点都被低估。N20持久留出四模型 MAPE 为2.57%–9.86%，G3 full三块均低估，最大偏差0.581s。G3 D/N记账内存模型因覆盖门槛后不可辨识而BLOCKED，没有降低门槛或使用留出值补齐。详见实际模型与全部预测误差 (`../07_cost_model/results-v2.md`, omitted from this source release)；没有把留出点回填训练后声称预测准确。模型没有覆盖任意并发、任意COW和在线到达过程，资源压力下的拒绝/OOM也不是连续延迟公式能够替代的。

## 12. 失败、限制与下一步证据

保留的关键负结果包括：旧density-v1遗漏域内Z采样，正式资源结论重跑v2；mixed首pilot因第二会话参考目录重入失败，产品H尚未启动；Tool原生首pilot错误处理正常末端EOF；故障SIGKILL截断一条COST尾记录，只标未观测而不补时长；96MiB失败；G4单请求反向样本；C8平台及批尾响应变慢；内存模型失配。检查器开发期错误与产品错误分开，不拼接不同源码局部PASS。

当前最值得联合考虑的决策有：任务是否允许留域、预计同域复用密度K、模板初始化成本与兼容范围、等待已有Worker还是派生新Worker、并发是否已超过收益平台、共同根预算能否同时容纳模板和工作进程、模板切换是否会反复支付初始化。对于最终exec的工作，应单独评估原生入口；对于要求新进程状态边界的任务，不能直接换成G4。

本轮没有实现调度算法、预测自然Agent调用频率或证明新的论文创新。它提供了多个真实交叉点和失败边界，足以支撑下一轮在明确合同下研究选择策略；不足以写死K阈值、推广任意依赖或宣称生产级可靠性。
